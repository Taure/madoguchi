# 7. Target protocol revision 2025-11-25 with version negotiation

Date: 2026-06-01

## Status

Accepted. Supersedes the single-revision stance of ADR 0001.

## Context

ADR 0001 fixed the server to exactly one MCP revision, `2025-06-18`, and
`negotiate/1` echoed that one value. MCP has since published `2025-11-25`, which
adds capabilities clients now expect (notably `icons` metadata on tools,
resources, prompts, and the server implementation, and JSON Schema 2020-12 as
the assumed schema dialect). We want to target the current revision without
dropping clients - including gakudan's - that still speak `2025-06-18`.

## Decision

Target `2025-11-25` and negotiate `2025-06-18` as a fallback.

- `madoguchi_dispatch` defines `?PROTOCOL` as `2025-11-25` and `?SUPPORTED` as
  `[2025-11-25, 2025-06-18]` (newest first). `protocol_version/0` returns the
  default; `supported_versions/0` returns the list the HTTP transport uses to
  gate the `MCP-Protocol-Version` header (ADR 0002).
- `negotiate/1` echoes the client's requested `protocolVersion` when it is in
  `?SUPPORTED`, otherwise advertises `?PROTOCOL` and lets the client decide.
- **`icons` metadata.** Optional `icons/0` callbacks on `madoguchi_tool` and
  `madoguchi_prompt`, surfaced in `tools/list` / `prompts/list` when exported.
  Resource descriptors carry `icons` directly in the maps a provider returns.
  The server definition may carry `title` and `icons`, surfaced in the
  `initialize` `serverInfo`. All are additive and omitted when absent.
- **JSON Schema 2020-12.** The framework does not validate schemas, so it
  imposes no dialect; `2025-11-25` assumes 2020-12 for `input_schema/0` and
  `output_schema/0`, which is documented as the convention. No code change is
  needed beyond saying so.

The two revisions are wire-compatible for everything madoguchi implements: the
`2025-11-25` additions are optional fields a `2025-06-18` client ignores, so one
code path serves both and the negotiated version only changes the value echoed
in `initialize`.

## Consequences

**Positive.** New clients get the current revision and its metadata; older
clients (gakudan's `2025-06-18` client, existing third-party clients) keep
working via negotiation. Adding a future revision is a one-line change to
`?PROTOCOL` / `?SUPPORTED` plus any new optional fields.

**Negative.** Supporting two revisions from one code path relies on the
additions being optional and backward-compatible; a future revision with a
breaking change would need branching on the negotiated version, which this design
does not yet do. The framework still does not validate schemas against 2020-12 -
the dialect is a documented convention, not an enforced contract.
